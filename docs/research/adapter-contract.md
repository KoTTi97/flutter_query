# The adapter contract: what upstream's own framework bindings need from `query-core`

- **Date:** 2026-09-08
- **Upstream revision:** TanStack Query `50680b98c` (`50680b98c4dc5ac4d97f7762014fa83f09a41d9a`, `origin/main`)
- **Ticket:** https://github.com/KoTTi97/flutter_query/issues/4
- **Sources:** read-only from the upstream clone at `query/`. Citations are `packages/<pkg>/src/<file>:<line>` at that revision. `docs/framework/*` is cited only for stated intent.

## Question

What is the minimal contract `query-core` expects from a framework binding? Answered by reading the five adapters the ticket names (`react-query`, `vue-query`, `solid-query`, `svelte-query`, `angular-query-experimental`) point by point, then cross-checking against the two adapters it does not name (`preact-query`, a near-copy of react; `lit-query`, the newest and most "framework-neutral" one) to separate the true contract from React habits.

## 0. The core side of the contract (what the adapters are talking to)

Before the per-adapter sections, the four core mechanisms every point below hangs off:

- **Subscription drives everything.** `Subscribable.subscribe(listener)` adds the listener, calls `onSubscribe()`, and returns an unsubscribe closure that calls `onUnsubscribe()` (`packages/query-core/src/subscribable.ts:8-17`). `QueryObserver.onSubscribe` on the *first* listener does `addObserver`, then either starts the mount fetch or `updateResult()`, then arms the stale/interval timers (`packages/query-core/src/queryObserver.ts:110-122`). `onUnsubscribe` with no listeners left calls `destroy()` (`:124-128`), which clears timers and `removeObserver`s (`:161-166`); the query then cancels/`scheduleGc`s when its last observer leaves (`packages/query-core/src/query.ts:523-548`). So "subscribe on attach, unsubscribe on detach" *is* fetch-on-mount, refetch timers, and garbage collection.
- **`setOptions` is the only update path.** It re-defaults the options, re-resolves the query (switching on key change), notifies `observerOptionsUpdated`, fetches if `shouldFetchOptionally` and there are listeners, calls `updateResult()`, and re-arms timers (`packages/query-core/src/queryObserver.ts:182-264`). The constructor itself calls `setOptions` (`:103`), so a freshly built observer already has a `#currentResult`.
- **The optimistic result is an options flag, not just a method.** `createResult` only applies the "will fetch on mount / will refetch after this option change" pre-state when `options._optimisticResults` is set (`:586-604`), and forces `fetchStatus: 'idle'` when it is `'isRestoring'` (`:601-603`). `getOptimisticResult(options)` builds the query, computes that result, and — when it differs — *moves the observer's `#currentResult` cursor* so select memoisation and structural sharing stay in sync across a key change (`:272-307`). The flag is declared `@internal` (`packages/query-core/src/types.ts:520-521`) yet every adapter sets it (matrix in §7).
- **Notification gating lives in core.** `updateResult` compares shallowly, then notifies listeners only if `notifyOnChangeProps === 'all'`, or nothing was ever tracked, or a tracked/listed prop changed (`packages/query-core/src/queryObserver.ts:735-806`); `trackResult` is the `Proxy` that records reads into `#trackedProps` (`:331-352`). Listener calls and the `observerResultsUpdated` cache event are wrapped in `notifyManager.batch` (`:792-805`). `notifyManager` itself batches while a transaction is open and otherwise schedules through `scheduleFn`, default `setTimeout(0)` (`packages/query-core/src/notifyManager.ts:19-53`).
- **`QueryClient.mount()` / `unmount()` is refcounted** and is the *only* place core subscribes to `focusManager` and `onlineManager` (`packages/query-core/src/queryClient.ts:104-136`); the managers install `window` listeners lazily on first subscriber (`packages/query-core/src/focusManager.ts:22-50`, `packages/query-core/src/onlineManager.ts:23-55`). `defaultQueryOptions` also carries two adapter-motivated defaults: `throwOnError ??= !!suspense` and `refetchOnReconnect ??= networkMode !== 'always'` (`packages/query-core/src/queryClient.ts:1026-1032`).

## 1. `react-query`

Files: `useBaseQuery.ts`, `useQuery.ts`, `useMutation.ts`, `QueryClientProvider.tsx`, `useIsFetching.ts`, `useMutationState.ts`, `useQueries.ts`, `IsRestoringProvider.ts`, plus `suspense.ts`, `errorBoundaryUtils.ts`, `HydrationBoundary.tsx`.

1. **Observer lifetime.** The observer is created lazily in render, before first commit, via `React.useState(() => new Observer(client, defaultedOptions))` (`packages/react-query/src/useBaseQuery.ts:86-92`) and lives as long as the component instance. Subscription is `useSyncExternalStore`'s subscribe callback — i.e. after commit — `observer.subscribe(notifyManager.batchCalls(onStoreChange))`, or `noop` when `shouldSubscribe` is false (`:97-103`); immediately after subscribing it calls `observer.updateResult()` "to make sure we did not miss any query updates between creating the observer and subscribing to it" (`:105-107`). The returned unsubscribe runs on unmount or whenever `[observer, shouldSubscribe]` changes (`:109-111`). Mutations follow the same shape: `useState(() => new MutationObserver(...))` (`packages/react-query/src/useMutation.ts:202-207`) and uSES subscribe with `batchCalls` (`:214-221`).
2. **`setOptions`.** `React.useEffect(() => observer.setOptions(defaultedOptions), [defaultedOptions, observer])` (`packages/react-query/src/useBaseQuery.ts:117-119`). Because `client.defaultQueryOptions(options)` (`:54`) spreads into a new object on every call (`packages/query-core/src/queryClient.ts:1011-1016`), this effect runs after *every* render; core's shallow-equality check inside `setOptions` (`packages/query-core/src/queryObserver.ts:211-220`) is what keeps that cheap. The gap between render and effect is filled by `getOptimisticResult` (point 4). `useMutation` does the same with un-defaulted options (`packages/react-query/src/useMutation.ts:210-212`); `useQueries` calls `observer.setQueries(...)` in an effect (`packages/react-query/src/useQueries.ts:447-451`).
3. **Batching / delivery.** Delivery is `useSyncExternalStore` with `getSnapshot = observer.getCurrentResult` (`packages/react-query/src/useBaseQuery.ts:98-115`); the store-change callback is wrapped in `notifyManager.batchCalls` (`:102`), so React is poked once per `notifyManager` flush (`packages/query-core/src/notifyManager.ts:32-53, 78-86`) rather than once per listener call. **No adapter calls `setBatchNotifyFunction`, `setScheduler` or `setNotifyFunction` in production code at this revision** — the only callers are test setups wrapping notifications in `act` (`packages/react-query/test-setup.ts:13-16`; matrix in §7). `useIsFetching` is uSES over `queryCache.subscribe(notifyManager.batchCalls(onStoreChange))` with `client.isFetching(filters)` as the snapshot (`packages/react-query/src/useIsFetching.ts:51-59`). `useMutationState` subscribes to the mutation cache, recomputes `mutationCache.findAll(filters).map(select ?? state)`, keeps the reference stable with `replaceEqualDeep`, and only then `notifyManager.schedule(onStoreChange)` (`packages/react-query/src/useMutationState.ts:176-193`).
4. **`getOptimisticResult` / `trackResult` / `notifyOnChangeProps`.** `defaultedOptions._optimisticResults` is set every render to `'isRestoring'`, `'optimistic'`, or `undefined` when `subscribed: false` (`packages/react-query/src/useBaseQuery.ts:73-80`); `observer.getOptimisticResult(defaultedOptions)` is called every render with the comment "this must be called before useSyncExternalStore" (`:94-95`). The hook returns `observer.trackResult(result)` unless `notifyOnChangeProps` is set (`:139-142`). `useQueries` gets the tuple `[optimisticResult, getCombinedResult, trackResult]` from `QueriesObserver.getOptimisticResult` (`packages/react-query/src/useQueries.ts:428-432`; `packages/query-core/src/queriesObserver.ts:238-262`) and returns `getCombinedResult(trackResult())` (`packages/react-query/src/useQueries.ts:493`). *Without them:* the first render would show `fetchStatus: 'idle'` (the fetch only starts in `onSubscribe`/the effect), the result cursor would not move on a key change (the long comment at `packages/query-core/src/queryObserver.ts:286-301`), and with an empty `#trackedProps` core notifies on *every* result change (`:767-772`) — so every `isFetching`/`isStale` flip would re-render. Stated intent: `docs/framework/react/guides/render-optimizations.md:18-24`.
5. **`focusManager` / `onlineManager`.** The adapter never references either (matrix, §7). `QueryClientProvider` calls `client.mount()` in an effect and `client.unmount()` in its cleanup (`packages/react-query/src/QueryClientProvider.tsx:74-79`), which is where core subscribes to both managers (`packages/query-core/src/queryClient.ts:104-120`). Platform wiring is left to the app: React Native docs tell users to call `onlineManager.setEventListener(...)` and `focusManager.setFocused(...)` from `AppState` (`docs/framework/react/react-native.md:26-88`).
6. **Client provision.** `QueryClientContext` (`packages/react-query/src/QueryClientProvider.tsx:9-11`); `useQueryClient(queryClient?)` returns the explicit argument if given, else context, else throws (`:21-33`). Every hook takes an optional trailing `queryClient` (`packages/react-query/src/useQuery.ts:287-293`).
7. **`isRestoring` / hydration.** `IsRestoringContext` defaults to `false` (`packages/react-query/src/IsRestoringProvider.ts:4-19`); `PersistQueryClientProvider` sets it `true` until `persistQueryClientRestore` settles (`packages/react-query-persist-client/src/PersistQueryClientProvider.tsx:25-53`). Effect in the hook: `_optimisticResults = 'isRestoring'` (`packages/react-query/src/useBaseQuery.ts:76-77`, core forces `fetchStatus: 'idle'` at `packages/query-core/src/queryObserver.ts:601-603`) and `shouldSubscribe = !isRestoring && subscribed` (`:97`), so no subscription — hence no fetch — while restoring; when it flips, uSES re-subscribes because `shouldSubscribe` is a dependency (`:111`). `HydrationBoundary` calls `hydrate(client, { queries: newQueries })` for *new* queries during render (`packages/react-query/src/HydrationBoundary.tsx:115-162`) and defers existing-but-newer queries to an effect so transitions do not repaint early (`:164-168`).
8. **`select` / `placeholderData` / `throwOnError`.** `select` and `placeholderData` are pure pass-through — core computes both in `createResult` (`packages/query-core/src/queryObserver.ts:612-686`); the only adapter touch is `useSuspenseQuery` forcing `placeholderData: undefined`, `enabled: true`, `suspense: true`, `throwOnError: defaultThrowOnError` (`packages/react-query/src/useSuspenseQuery.ts:90-100`, `packages/react-query/src/suspense.ts:11-19`). `throwOnError` is evaluated in render with `getHasError` — `isError && !errorResetBoundary.isReset() && !isFetching && query && ((suspense && data === undefined) || shouldThrowError(throwOnError, [error, query]))` (`packages/react-query/src/errorBoundaryUtils.ts:51-77`) — and then `throw result.error` (`packages/react-query/src/useBaseQuery.ts:126-137`); `useMutation` throws when `shouldThrowError(observer.options.throwOnError, [result.error])` (`packages/react-query/src/useMutation.ts:238-242`). Suspense is a render-phase `throw fetchOptimistic(...)` (`packages/react-query/src/useBaseQuery.ts:121-124`, `packages/react-query/src/suspense.ts:49-75`), with two adapter-side option rewrites: `ensureSuspenseTimers` clamps `staleTime`/`gcTime` to >= 1000 ms (`packages/react-query/src/suspense.ts:21-47`) and `ensurePreventErrorBoundaryRetry` sets `retryOnMount = false` while an error boundary has not been reset (`packages/react-query/src/errorBoundaryUtils.ts:13-41`).

React-only extras worth naming: the `subscribed` option (`packages/react-query/src/types.ts:65, 259`; `useBaseQuery.ts:73`), `QueryErrorResetBoundary` (`packages/react-query/src/QueryErrorResetBoundary.tsx:18-40, 136-145`), and `useIsMutating` being `useMutationState({ filters: { ...filters, status: 'pending' } }).length` (`packages/react-query/src/useMutationState.ts:35-44`). `preact-query` is a line-for-line copy with `preact/hooks` and its own `useSyncExternalStore` shim, minus the `subscribed` option (diff of the two `useBaseQuery.ts` files).

## 2. `vue-query`

Files: `useBaseQuery.ts`, `useMutation.ts`, `useQueryClient.ts`, plus `vueQueryPlugin.ts`, `queryClient.ts`, `utils.ts`, `useQueries.ts`.

1. **Observer lifetime.** Created synchronously in `setup()`: `new Observer(client, defaultedOptions.value)` (`packages/vue-query/src/useBaseQuery.ts:118`), with a dev warning if there is no active effect scope (`:82-88`). Subscription is immediate — `watch(client.isRestoring, (isRestoring) => { if (!isRestoring) { unsubscribe(); unsubscribe = observer.subscribe(...) } }, { immediate: true })` (`:128-141`); the guard `if (client.isRestoring)` is always true because vue's `QueryClient` subclass initialises `isRestoring = ref(false)` (`packages/vue-query/src/queryClient.ts:58`). Teardown is `onScopeDispose(() => unsubscribe())` (`packages/vue-query/src/useBaseQuery.ts:150-152`). There is no post-subscribe `updateResult()`; the listener writes straight into reactive state (`:134-136`). Mutations: observer built in setup (`packages/vue-query/src/useMutation.ts:253`), subscribed immediately (`:258-260`), disposed with the scope (`:276-278`).
2. **`setOptions`.** Options are a `computed` that unwraps getters/refs with `cloneDeepUnref`, eagerly resolves a function-valued `enabled`, defaults through `client.defaultQueryOptions`, and stamps `_optimisticResults` (`packages/vue-query/src/useBaseQuery.ts:92-116`). `watch(defaultedOptions, updater)` where `updater` is `observer.setOptions(defaultedOptions.value); updateState(state, observer.getCurrentResult())` (`:143-148`). Two workaround call sites also force `setOptions` first: the wrapped `refetch` (fix #5910, `:154-158`) and `suspense()` (fix #6133, `:166-169`). Mutation: `watch(defaultedOptions, () => observer.setOptions(defaultedOptions.value))` (`packages/vue-query/src/useMutation.ts:272-274`).
3. **Batching / delivery.** `vue-query` never imports `notifyManager` (matrix, §7). The listener copies each key of the result into a `reactive()`/`shallowReactive()` object via `updateState` (`packages/vue-query/src/useBaseQuery.ts:120-122, 134-136`; `packages/vue-query/src/utils.ts:14-21`); Vue's scheduler coalesces the re-render. The public surface is `toRefs(readonly(state))` with the function members copied raw (`packages/vue-query/src/useBaseQuery.ts:220-235`). Core's own `notifyManager.batch` around listener calls still applies.
4. **Optimistic / tracking.** `_optimisticResults` is set (`:111-113`) but `getOptimisticResult` is only called inside `suspense()` (`:170-172`). The initial state is `observer.getCurrentResult()` (`:120-122`), which already carries the optimistic fetching pre-state because the constructor's `setOptions` -> `updateResult` -> `createResult` reads the flag from `this.options` (`packages/query-core/src/queryObserver.ts:103, 238, 587`). No `trackResult`, no `notifyOnChangeProps` handling: property-level tracking is done by Vue's `toRefs` — a component only depends on the refs it reads.
5. **`focusManager` / `onlineManager`.** `VueQueryPlugin.install` calls `client.mount()` unless `environmentManager.isServer()` (`packages/vue-query/src/vueQueryPlugin.ts:87-89`) and `client.unmount()` from `app.onUnmount` / a patched `app.unmount` (`:109-122`). Vue is the only adapter that reads `environmentManager` (matrix).
6. **Client provision.** `app.provide(getClientKey(queryClientKey), client)` (`packages/vue-query/src/vueQueryPlugin.ts:146`, Vue 2 mixin at `:124-144`); `useQueryClient(id)` requires an injection context and `inject`s the keyed client (`packages/vue-query/src/useQueryClient.ts:27-45`); multiple clients are keyed by string (`packages/vue-query/src/utils.ts:8-11`). The plugin can construct the client itself (`vueQueryPlugin.ts:79-85`). Vue subclasses `QueryClient` to `cloneDeepUnref` every argument (`packages/vue-query/src/queryClient.ts:44-62`).
7. **`isRestoring` / hydration.** Restoration is a `Ref` on the client (`packages/vue-query/src/queryClient.ts:58`) driven by the plugin's `clientPersister` (`packages/vue-query/src/vueQueryPlugin.ts:95-107`); the consumer watch above re-subscribes when it turns false, and `useQueries` does the same (`packages/vue-query/src/useQueries.ts:447-462`). There is no `HydrationBoundary` and no `hydrate` call in `vue-query/src` (matrix) — SSR hydration is left to the app/Nuxt calling core's `hydrate`.
8. **`select` / `placeholderData` / `throwOnError`.** `select` and `placeholderData` are core. `throwOnError` is checked in a `watch(() => state.error, ...)` that throws when `state.isError && !state.isFetching && shouldThrowError(throwOnError, [error, observer.getCurrentQuery()])` (`packages/vue-query/src/useBaseQuery.ts:203-218`), delegating to Vue's `errorCaptured`; the mutation composable does the same (`packages/vue-query/src/useMutation.ts:288-298`). Suspense is an explicit `suspense()` promise for `<Suspense>`: `setOptions`, `getOptimisticResult`, then `fetchOptimistic` if stale else resolve immediately, rejecting only if `shouldThrowError` says so (`packages/vue-query/src/useBaseQuery.ts:160-201`). Vue is one of two adapters (with lit) that calls `client.defaultMutationOptions` itself (`packages/vue-query/src/useMutation.ts:249-252`).

## 3. `solid-query`

Files: `useBaseQuery.ts` (the ticket's `createBaseQuery.ts` — renamed at this revision), `QueryClientProvider.tsx`, `isRestoring.ts`, `useMutation.ts`, `QueryClient.ts`.

1. **Observer lifetime.** Created synchronously in a signal: `createSignal(new Observer(client(), defaultedOptions()))` (`packages/solid-query/src/useBaseQuery.ts:141-143`), recreated (with unsubscribe/resubscribe) when the client accessor changes (`:315-330`). Subscription happens *inside the `createResource` fetcher*: on the client, `createClientSubscriber()` when `!unsubscribe && !isRestoring()` followed by `obs.updateResult()` (`:237-247`); on the server, `createServerSubscriber` resolves/rejects the resource from the first notification (`:149-169`). Teardown is `onCleanup` (`:344-357`), deliberately deferred on the server while the resource is still loading (`:121-125, 229-235, 345-348`). Mutations: observer built in the body (`packages/solid-query/src/useMutation.ts:185-190`), subscribed immediately (`:227-233`), `onCleanup(unsubscribe)` (`:235`).
2. **`setOptions`.** A synchronous reactive computation: `createComputed(on([observer, defaultedOptions], ([obs, opts]) => { obs.setOptions(opts); setStateWithReconciliation(obs.getOptimisticResult(opts)); refetch() }, { defer: true }))` (`:359-369`) — `defer: true` skips the initial run because the constructor already applied them. `onHydrated` also calls `setOptions` with `refetchOnMount: false` when hydrated data is fresh enough (`:299-310`). Mutation: `createComputed(() => observer.setOptions(options()))` (`packages/solid-query/src/useMutation.ts:209-211`).
3. **Batching / delivery.** The client listener stores the result and `queueMicrotask(() => refetch())` re-runs the resource (`:178-188`); the resource's `storage` is a Solid store written through `setState(reconcile(...))` (`:190-203, 205-222`). `notifyManager.batchCalls` is used only in the server subscriber (`:155-168`). Core's `notifyManager` docs give `notifyManager.setBatchNotifyFunction(batch)` with Solid's `batch` as *the* example (`packages/query-core/src/notifyManager.ts:99-114`) — but `solid-query` does not call it at this revision (matrix).
4. **Optimistic / tracking.** `getOptimisticResult` seeds the store at creation (`:145-147`) and on every option change (`:364`) and after hydration (`:309`); `_optimisticResults` is set (`:129-131`). Solid forces `structuralSharing = false` (`:132`) and replaces it with its own `reconcile` option (`:27-60`; the option type omits `structuralSharing` and adds `reconcile`, `packages/solid-query/src/QueryClient.ts:23-51`). No `trackResult`/`notifyOnChangeProps` — the store is fine-grained. On the server it also forces `retry = false` and `throwOnError = true` (`:133-136`).
5. **`focusManager` / `onlineManager`.** `QueryClientProvider` mounts in a `createRenderEffect` (unmounting a previous client first) and unmounts on `onCleanup` (`packages/solid-query/src/QueryClientProvider.tsx:98-103`).
6. **Client provision.** The context value is an *accessor* `() => QueryClient` (`:13-15, 106`); `useQueryClient(queryClient?)` prefers the argument (`:28-39`); `useQueryClientResolver` returns an accessor so the client itself is reactive (`:41-58`), which is what lets `useBaseQuery` recreate its observer.
7. **`isRestoring` / hydration.** `IsRestoringContext` holds an accessor defaulting to `() => false` (`packages/solid-query/src/isRestoring.ts:4-19`); the persist provider supplies a signal (`packages/solid-query-persist-client/src/PersistQueryClientProvider.tsx:20-49`). A `createComputed(on(isRestoring, ...))` calls `refetch()` when restoring ends, which re-enters the fetcher and subscribes (`packages/solid-query/src/useBaseQuery.ts:332-342, 244-246`). Hydration is per-query and streaming rather than a boundary: on the server `hydratableObserverResult` strips functions and attaches `hydrationData` (`:66-100`); on the client `onHydrated` calls core `hydrate(client(), { queries: [hydrationData] })` (`:286-292`).
8. **`select` / `placeholderData` / `throwOnError`.** Core computes the first two. `throwOnError` is evaluated inside the resource fetcher — `isError && !isFetching && !isRestoring() && shouldThrowError(throwOnError, [error, obs.getCurrentQuery()])` -> `reject(error)` (`:249-260`) — so Solid's `ErrorBoundary` catches it; suspense is inherent in `createResource` (resolved only once `!observerResult.isLoading`, `:261-266`). Mutation errors are thrown from a `createComputed(on(() => state.status, ...))` (`packages/solid-query/src/useMutation.ts:213-225`).

## 4. `svelte-query`

Files: `createBaseQuery.svelte.ts`, `createMutation.svelte.ts`, `QueryClientProvider.svelte`, `context.ts`, `useQueryClient.ts`, `useIsRestoring.ts`, `utils.svelte.ts`, `containers.svelte.ts`, `useHydrate.ts`.

1. **Observer lifetime.** `let observer = $state(new Observer(client, resolvedOptions))` in component init (`packages/svelte-query/src/createBaseQuery.svelte.ts:43-48`), rebuilt when the derived client changes (`:49-61`). Subscription is in a post-mount `$effect`: `observer.subscribe(() => update(createResult()))` unless `isRestoring.current`, followed by `observer.updateResult()`, returning the unsubscribe as the effect cleanup (`:74-80`). Mutations: `$state(new MutationObserver(client, options()))` (`packages/svelte-query/src/createMutation.svelte.ts:183-189`), subscribed in `$effect.pre` with cleanup (`:218-225`).
2. **`setOptions`.** `watchChanges(() => resolvedOptions, 'pre', () => observer.setOptions(resolvedOptions))` — an `$effect.pre` that skips its first run (`:82-88`; `packages/svelte-query/src/utils.svelte.ts:17-44`). A second watcher on `[resolvedOptions, observer]` re-derives the result to cover the restore race the comment describes (`:89-104`). Mutation: `$effect.pre(() => observer.setOptions(options()))` (`packages/svelte-query/src/createMutation.svelte.ts:199-201`).
3. **Batching / delivery.** No `notifyManager` on the query path (matrix; only `createMutation` wraps its assignment in `notifyManager.batchCalls(...)()` and invokes it immediately, `packages/svelte-query/src/createMutation.svelte.ts:218-225`). The result lives in a `createRawRef` proxy whose keys are individual `$state.raw` fields (`packages/svelte-query/src/containers.svelte.ts:29-136`); `update()` re-points every key lazily so that reading a key is what triggers the tracked-props proxy (the comment at `:118-125` explains that eager access would track everything). Svelte's scheduler does the rest.
4. **Optimistic / tracking.** `createResult()` is `observer.getOptimisticResult(resolvedOptions)` wrapped in `trackResult` unless `notifyOnChangeProps` is set (`packages/svelte-query/src/createBaseQuery.svelte.ts:63-68`); it is used for the initial value, in the subscription callback and after option changes (`:69-72, 77, 102`). `_optimisticResults` is set (`:35-39`). So svelte relies on core's tracking exactly like react, despite having fine-grained reactivity.
5. **`focusManager` / `onlineManager`.** `QueryClientProvider.svelte`: `onMount(() => client.mount())`, `onDestroy(() => client.unmount())`, defaulting to `new QueryClient()` when no client is passed (`packages/svelte-query/src/QueryClientProvider.svelte:7-18`).
6. **Client provision.** `setContext(Symbol('QueryClient'), client)` (`packages/svelte-query/src/context.ts:5, 45-47`), `getQueryClientContext` throws when missing (`:14-23`), `useQueryClient(queryClient?)` prefers the argument (`packages/svelte-query/src/useQueryClient.ts:4-7`); `createBaseQuery` wraps it in `$derived` so the client is reactive (`createBaseQuery.svelte.ts:32`).
7. **`isRestoring` / hydration.** A `Box<boolean>` in context, defaulting to `{ current: false }` even outside a component (`packages/svelte-query/src/context.ts:52-61`), set by the persist provider (`packages/svelte-query-persist-client/src/PersistQueryClientProvider.svelte:30-49`). Hydration: `useHydrate` calls core `hydrate(client, state, options)` synchronously during init (`packages/svelte-query/src/useHydrate.ts:33-43`; `HydrationBoundary.svelte:24`).
8. **`select` / `placeholderData` / `throwOnError`.** Core computes `select`/`placeholderData`. **`throwOnError` is not surfaced at all on the query path** — the only references in `svelte-query/src` are type-inference helpers (`packages/svelte-query/src/createQueries.svelte.ts:67, 116`); errors are returned as state. No suspense.

## 5. `angular-query-experimental`

Files: `create-base-query.ts`, `inject-query.ts`, `inject-mutation.ts`, `inject-query-client.ts`, `providers.ts`, `inject-is-restoring.ts`, `signal-proxy.ts`, `pending-tasks-compat.ts`, `inject-is-fetching.ts`, `inject-mutation-state.ts`.

1. **Observer lifetime.** The observer is a lazily-initialised singleton inside a `computed` — `instance ||= new Observer(queryClient, defaultedOptionsSignal())` — so it is created on first read (`packages/angular-query-experimental/src/create-base-query.ts:66-78`) and never recreated (the client is injected once, `:49`). `injectQuery` asserts an injection context or runs in the given injector (`packages/angular-query-experimental/src/inject-query.ts:200-208`). Subscription is an `effect`: `ngZone.runOutsideAngular(() => observer.subscribe(notifyManager.batchCalls(...)))`, skipped while `isRestoring()`, with `onCleanup` unsubscribing (`create-base-query.ts:108-154`); the effect re-runs (unsubscribe + resubscribe) when `isRestoring` flips, and its cleanup runs when the injector is destroyed. No post-subscribe `updateResult()` (matrix) — instead the exposed result is `subscriberResult ?? optimisticResult` (`:156-160`). Mutations mirror this (`packages/angular-query-experimental/src/inject-mutation.ts:201-212, 259-307`).
2. **`setOptions`.** An `effect` that reads `observerSignal()` and `defaultedOptionsSignal()` and calls `observer.setOptions(defaultedOptions)` under `untracked` (`create-base-query.ts:89-106`); its cleanup resets `resultFromSubscriberSignal` to `null` so the optimistic computed takes over until the next notification (`:97-99`). Angular effects run during change detection, so this is asynchronous relative to the option signal changing; the wrapped `refetch` therefore calls `setOptions` first (`:162-172`). Mutation: same effect (`inject-mutation.ts:245-257`).
3. **Batching / delivery.** `notifyManager.batchCalls` inside `runOutsideAngular`, then `ngZone.run` to write a `signal` (`create-base-query.ts:115-145`); the signal is exposed through `signalProxy`, which lazily creates one `computed` per property and passes functions through untouched (`packages/angular-query-experimental/src/signal-proxy.ts:14-46`). It also reports `fetchStatus === 'fetching'` as an Angular `PendingTask` for SSR/hydration stability (`create-base-query.ts:120-127`; `packages/angular-query-experimental/src/pending-tasks-compat.ts:9-28`). `injectIsFetching` and `injectMutationState` subscribe to the caches with `batchCalls` and only write when the value changed (`packages/angular-query-experimental/src/inject-is-fetching.ts:79-94`; `inject-mutation-state.ts:147-164`).
4. **Optimistic / tracking.** `getOptimisticResult` in a `computed` (`create-base-query.ts:80-82`), `_optimisticResults` set (`:58-64`). The comment "observer.trackResult is not used as this optimization is not needed for Angular" (`:109`; `inject-mutation.ts:261`) — because `signalProxy` gives per-property signals. The multi-query variant *does* use `trackResult()` through `QueriesObserver` (`packages/angular-query-experimental/src/inject-queries.ts:435-439`).
5. **`focusManager` / `onlineManager`.** `provideQueryClient` is a DI factory that calls `client.mount()` and registers `DestroyRef.onDestroy(() => client.unmount())` (`packages/angular-query-experimental/src/providers.ts:22-38`).
6. **Client provision.** Angular DI with `QueryClient` as the token (`providers.ts:26`); `inject(QueryClient)` in the base query (`create-base-query.ts:49`) and `injectQueryClient()` (`packages/angular-query-experimental/src/inject-query-client.ts:18-22`); `provideTanStackQuery(client, ...features)` bundles devtools/persist features (`providers.ts:102-110`).
7. **`isRestoring` / hydration.** `IS_RESTORING` injection token defaulting to `signal(false).asReadonly()` (`packages/angular-query-experimental/src/inject-is-restoring.ts:13-16`), overridden by `provideIsRestoring` (`:48-53`) from `withPersistQueryClient` (`packages/angular-query-persist-client/src/with-persist-query-client.ts:58-81`). No `hydrate` call in `angular-query-experimental/src` (matrix).
8. **`select` / `placeholderData` / `throwOnError`.** Core computes the first two. `throwOnError` is evaluated inside the subscription callback — `isError && !isFetching && shouldThrowError(throwOnError, [error, observer.getCurrentQuery()])` -> `ngZone.onError.emit(error); throw error` (`create-base-query.ts:129-139`); mutations likewise (`inject-mutation.ts:281-287`). No suspense.

## 6. Cross-check: `lit-query` (the framework-neutral control)

`lit-query` is a `ReactiveController`, so its lifecycle is the DOM's, not a render cycle. Observer built in the constructor only when an explicit client is given, else when the context client resolves in `syncClient()` (`packages/lit-query/src/createQueryController.ts:116-133, 228-249`). `hostConnected` (deferred a microtask, `packages/lit-query/src/controllers/BaseController.ts:57-66`) -> `refreshOptions(); subscribe(); observer.updateResult(); setObserverResult(getCurrentResult())` (`createQueryController.ts:135-146`); `hostDisconnected` -> unsubscribe (`:148-151`); `hostUpdate` -> `setOptions` before every host render when options are an accessor (`:153-159, 251-268`). The listener is a plain `observer.subscribe((next) => this.setResult(next))` — no `notifyManager` — and `setResult` requests a host update through a microtask (`:209-221`; `BaseController.ts:136-171`). `_optimisticResults = 'optimistic'` always (`createQueryController.ts:310-311`); `trackResult` when `!notifyOnChangeProps` via a small tracker (`packages/lit-query/src/queryObserverResultTracker.ts:15-29`). `mount()`/`unmount()` in `connectedCallback`/`disconnectedCallback` (`packages/lit-query/src/QueryClientProvider.ts:90-101, 140-165`). Client via `@lit/context` plus a module-level default registry (`packages/lit-query/src/context.ts:20-120`). No `isRestoring`, no `throwOnError`, no `hydrate`; it *does* call `client.defaultMutationOptions` (`packages/lit-query/src/createMutationController.ts:287-295`) and offers a vue-style `suspense()` (`createQueryController.ts:186-199`).

## 8. The distilled contract

### 8.1 What every adapter needs from core (the true contract)

Seven things, and only these, are used by all seven adapters:

1. **A shared `QueryClient` whose `mount()`/`unmount()` the binding calls exactly once per provider lifetime.** This is the whole of the focus/online wiring; no adapter touches `focusManager`/`onlineManager` directly (§7). Platform-specific event sources are the *app's* job through `setEventListener`/`setFocused` (`docs/framework/react/react-native.md:26-88`, `docs/framework/react/guides/window-focus-refetching.md:45-60`).
2. **`client.defaultQueryOptions(options)` (and, optionally, `defaultMutationOptions`) as the normalisation step**, plus the ability to stamp `_optimisticResults` on the result. Core's `QueryObserver.setOptions` re-defaults anyway (`packages/query-core/src/queryObserver.ts:194`), so the adapter-side call exists to get a `queryHash` and defaults *before* the observer exists — for `getOptimisticResult`, the cache lookup, and the optimistic flag.
3. **`new QueryObserver(client, defaultedOptions)` / `new MutationObserver(client, options)` — one per component instance,** rebuilt only when the client changes.
4. **`observer.subscribe(listener)` once the component is attached, and the returned unsubscribe on detach.** Core's `onSubscribe`/`onUnsubscribe` turn that into fetch-on-mount, timers and GC (`§0`). What breaks without it: nothing fetches, nothing refetches, nothing is garbage-collected.
5. **`observer.setOptions(defaultedOptions)` whenever inputs change.** Key switching, `enabled` flips, refetch-on-option-change and timer re-arming are all inside core; the adapter's only decision is *when* (react: after every commit; vue/solid/svelte/angular: when the reactive source changes; lit: before every host update).
6. **A synchronous read of the result — `getCurrentResult()`, and `getOptimisticResult(defaultedOptions)` when the first paint must already say "fetching".** Every adapter sets `_optimisticResults`; six of seven call `getOptimisticResult` (vue gets the same effect from the constructor path, §2.4).
7. **The `QueryObserverResult`/`MutationObserverResult` value delivered to the listener, copied by the adapter into its own reactive container.** Core never renders; it hands over an immutable snapshot with bound `refetch`/`mutate`/`reset` (`packages/query-core/src/queryObserver.ts:695-723`; `packages/query-core/src/mutationObserver.ts:224-238`).

For the global hooks, the contract is the caches: `queryCache.subscribe` + `client.isFetching(filters)` for is-fetching, and `mutationCache.subscribe` + `mutationCache.findAll(filters)` + `replaceEqualDeep` for mutation state (react, vue, solid, svelte, angular, lit all do exactly this; §1.3, §5.3).

### 8.2 Optional core APIs — used when the framework needs them

- **`notifyManager.batchCalls` / `schedule`.** Needed where the framework's "please re-render" entry point is not itself batched (React's `onStoreChange`, Angular's zone). Vue, Svelte's query path and Lit skip it because their reactivity systems coalesce writes. `setBatchNotifyFunction`/`setScheduler`/`setNotifyFunction` are *host* hooks — no adapter calls them; only test setups wrap notifications in `act` (`packages/react-query/test-setup.ts:13-16`).
- **`trackResult` + `notifyOnChangeProps`.** Needed when the framework re-renders a whole component per notification (React, Preact, Lit) — and Svelte chose to use it too. Skipped by Vue, Solid and Angular's single-query path, where per-property reactivity replaces it. Without it core notifies on every result change (`packages/query-core/src/queryObserver.ts:767-772`).
- **`updateResult()` after subscribing.** Closes the create->subscribe gap in frameworks where those are separate phases (react, preact, solid, svelte, lit). Vue subscribes synchronously, Angular falls back to the optimistic computed.
- **`fetchOptimistic`.** Exists for suspense-style APIs (react/preact render-phase throw; vue/lit `suspense()` promise).
- **`shouldThrowError`, `getCurrentQuery`.** Only for adapters that surface `throwOnError` (svelte and lit do not).
- **`hydrate`.** Only for adapters that own an SSR boundary (react/preact, svelte, solid's per-query variant).
- **`environmentManager.isServer`.** Only vue reads it; solid uses `solid-js/web`'s `isServer`.

### 8.3 React-specific parts (in the adapter, not core)

Suspense plumbing — `ensureSuspenseTimers`, `ensurePreventErrorBoundaryRetry` (`retryOnMount = false`), `QueryErrorResetBoundary`, `defaultThrowOnError`, the render-phase `throw` (`§1.8`); the `subscribed` option (`packages/react-query/src/types.ts:65, 259`); `useSyncExternalStore` as the delivery mechanism; hydrating new queries in render vs existing ones in an effect (`packages/react-query/src/HydrationBoundary.tsx:115-168`).

### 8.4 Things every adapter re-implements itself

- The reactive result container (uSES snapshot, `reactive()`, Solid store + `reconcile`, `createRawRef`, `signalProxy`, `requestUpdate`).
- The `isRestoring` channel (context / ref / accessor / box / DI token) — core only sees it as `_optimisticResults: 'isRestoring'` and the adapter's decision not to subscribe.
- `mutate` as a void wrapper: `observer.mutate(vars, opts).catch(noop)` plus `mutateAsync: result.mutate` — identical in all seven (`packages/react-query/src/useMutation.ts:232, 244`; `packages/vue-query/src/useMutation.ts:262-270, 303`; `packages/solid-query/src/useMutation.ts:192-199`; `packages/svelte-query/src/createMutation.svelte.ts:203-207, 233`; `packages/angular-query-experimental/src/inject-mutation.ts:214-225, 318`; `packages/lit-query/src/createMutationController.ts:193-218`).
- `isMutating` = `mutationState` filtered to `status: 'pending'`, counted (`packages/react-query/src/useMutationState.ts:35-44`; `packages/vue-query/src/useMutationState.ts:63-75`).
- Where and when `throwOnError` is evaluated (render / watcher / fetcher / listener) and how the error reaches the framework's boundary.
- Option normalisation for the framework's reactivity model (`cloneDeepUnref`, accessors, functions, `$derived`).
- Observer recreation when the client changes (solid, svelte, lit).

### 8.5 Core API that exists only to serve one adapter (or one style)

- `_optimisticResults: 'isRestoring'` and the `fetchStatus: 'idle'` override (`packages/query-core/src/queryObserver.ts:601-603`) — exists for the persist-client restore window; lit does not use it.
- `QueriesObserver.getOptimisticResult` returning a `[result, combine, trackResult]` tuple (`packages/query-core/src/queriesObserver.ts:238-262`) — shaped for React's render phase; vue ignores the third element.
- `throwOnError ??= !!suspense` in `defaultQueryOptions` (`packages/query-core/src/queryClient.ts:1030-1032`), the `suspense` option itself (`packages/query-core/src/types.ts:501-507`), and `fetchOptimistic` — all for React-style suspense.
- `retryOnMount` — read by core's `shouldLoadOnMount` (`packages/query-core/src/queryObserver.ts:837-849`) but *set* only by React's error-boundary logic.
- `notifyManager.setBatchNotifyFunction` / `setScheduler` / `setNotifyFunction` — documented as adapter hooks (`packages/query-core/src/notifyManager.ts:92-135`) but at this revision only test harnesses use them.
- `trackProp` (public) — used only by `QueriesObserver` and lit's queries controller (matrix).
- `Query.observers` bookkeeping / `observerAdded`/`observerRemoved`/`observerOptionsUpdated` cache events — consumed by devtools, not by the bindings.

### 8.6 What this implies for a Flutter binding (inference, not upstream fact)

The seven-item contract in §8.1 maps onto a `StatefulWidget`/`State` directly: create the observer in `initState` (or lazily on first `build`), `subscribe` in `initState`/after first frame, `setOptions` in `didUpdateWidget`, unsubscribe in `dispose`, and call `mount()`/`unmount()` from an inherited scope widget. Whether the Dart port needs `trackResult` is the React-vs-Vue question: a `Builder` that rebuilds its whole subtree per notification is in React's position and wants tracking or an explicit `notifyOnChangeProps`; a `ValueListenable`-per-field design is in Vue's position and does not. `batchCalls` matters only if the binding's "please rebuild" call (`setState`) is not already coalesced per frame — Flutter's is, so a `scheduleFn` that defers to the next microtask/frame is the closer analogue to what react-query gets from `setTimeout(0)`.
