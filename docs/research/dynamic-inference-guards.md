# Guards against a type argument silently inferring to `dynamic`

- Date: 2026-09-11
- Ticket: https://github.com/KoTTi97/flutter_query/issues/34 (part of #33; finding **C1** of the 2026-09-10 deep-dive, section 2.1)
- Scope: what the Dart language, the analyzer and the lint sets offer against a type parameter that appears only in an optional callback inferring to `dynamic`; which language-level shapes actually stop it at the call site; how riverpod, bloc, `flutter_hooks` and `signals` shape their generics; and whether Dart 3.11–3.13 changed anything.

**Summary.** Nothing in Dart lets a *library* stop this at its consumers' call sites: the only diagnostic that catches it, `inference_failure_on_instance_creation`, is produced by the `strict-inference` analyzer mode, which is off by default, absent from `lints/recommended` and `flutter_lints`, and scoped to the package whose `analysis_options.yaml` enables it — a dependent package with default lints sees `No issues found!` (verified locally, and by the deep-dive's `consumer_probe` against the real `query_kit`). The language-level answer is structural: every comparable library puts the output type parameter in a *required* parameter (creator, selector, builder, initial value), so inference always has a source, and the optional-callback case that matches ours — riverpod's `select`, bloc's `BlocSelector` — is a *separate entry point* whose selector is required. A bound (`TData extends Object?`) is worse than nothing (the slot becomes `Object?` *and* the warning goes away, an open analyzer bug), a static factory leaves the trap in the still-public constructor, and `assert(TData != dynamic)` only runs with asserts on and misses `Object?`. Dart 3.11–3.13 changed nothing about type-argument inference; 3.13 replaced `strict-raw-types` and `strict-casts` with lint rules but left `strict-inference` as an analyzer mode.

## The local experiment

Dart 3.10.7 (stable, macos_arm64), a throwaway package modelling the port's shape — `QueryObserverOptions<TQueryData, TData>` with `TData` only in `select` (`packages/query_kit/lib/src/query_options.dart:420-460`), `QueryController<TQueryData, TData>` and `QueryController.create<TData>(client, QueryObserverOptions<TData, TData>)` (`packages/query_kit_flutter/lib/src/query_controller.dart:50-88`), `QueryBuilder<TData>` taking `QueryObserverOptions<TData, TData>` (`packages/query_kit_flutter/lib/src/query_builder.dart:37-50`) — analysed once with `strict-casts`/`strict-inference`/`strict-raw-types` on and once with `package:lints/recommended.yaml` (lints 6.1.0) only, then run. The model:

```dart
class Opts<TQueryData, TData> {
  const Opts({required this.queryKey, this.queryFn, this.select});
  final List<Object?> queryKey;
  final Future<TQueryData> Function()? queryFn;
  final TData Function(TQueryData data)? select;
}
class Controller<TQueryData, TData> {
  Controller(this.opts);
  static Controller<TData, TData> create<TData>(Opts<TData, TData> opts) => Controller<TData, TData>(opts);
  Type get dataType => TData;
}
```

## 1. What the analyzer offers

**The modes.** `strict-inference`, `strict-raw-types` and `strict-casts` are *language modes*, not lints: they live under `analyzer: language:` in `analysis_options.yaml`, "can be used together or separately; all default to false" (https://dart.dev/tools/analysis, "Enabling additional type checks"). The page defines `strict-inference` as "A value of `true` ensures that the type inference engine never chooses the `dynamic` type when it can't determine a static type", and `strict-raw-types` as the same restricted to "omitted type arguments" — i.e. `List numbers = …` written as a raw type, which is not the C1 shape (nothing in `QueryObserverOptions(queryKey: …)` is a raw type; the type arguments are absent from an *invocation*, which is `strict-inference`'s territory). The normative definitions are in the language repository: `resources/type-system/strict-inference.md` (https://github.com/dart-lang/language/blob/main/resources/type-system/strict-inference.md) and `strict-raw-types.md`.

**Which cases `strict-inference` flags.** The design doc's "Conditions for strict inference failure" section lists: uninitialized variables without a type, untyped function parameters, under-constrained collection literals, instance creation, generic function calls, and function return types. Instance creation is the C1 case verbatim: "Instantiating a generic class without explicit type argument(s), in which one or more type arguments cannot be inferred from downwards or upwards inference is considered an inference failure. This includes type parameters with an explicit bound." The experiment confirms the first sentence for a type parameter that only appears in an *omitted optional named parameter* (rows A1–A4, A8): the warning is reported on the constructor invocation (`Opts`), not on the consumer, and a downward context from `create(Opts<T, T>)` does not help because `T` is itself unconstrained there. An explicit type argument on the consumer (A6) or a declared return type on a factory function (A7) — the two things the port's docs already do, unknowingly load-bearing — both cure the type and silence the warning.

**Which cases it does *not* flag: bounded type parameters.** The doc's second sentence is not what the analyzer does. In the experiment `class D<T extends num> {} var d = D();` (the doc's own example, marked "Inference failure") is clean and instantiates `D<num>`; `DO<T extends Object?>` is clean and gives `Object?`; the port's shape with `TData extends Object?` / `extends Object` is clean and gives `Object?` / `Object` (rows E1, F1). The cause is visible in the implementation: `pkg/analyzer/lib/src/dart/element/generic_inferrer.dart` (SDK `main` at `114103db1200`, 2026-09-11) records a type parameter as inferred when `_typeSystemOperations.isKnownType(inferred)` and only otherwise, under `_strictInference`, calls `_reportInferenceFailure` (lines 408-420, comment: "[typeParam] could not be inferred. A result will still be returned by [infer], with [typeParam] filled in as its bounds. This is considered a failure of inference, under the 'strict-inference' mode."). A slot with a bound resolves to the bound, which is a known type, so it never reaches the report. This is tracked as dart-lang/sdk#52640 "strict-inference does not report types with bound type parameters" (open since 2023-06-08, P3, `type-enhancement`; https://github.com/dart-lang/sdk/issues/52640), and the doc/implementation drift generally as dart-lang/sdk#45371 (open since 2021; https://github.com/dart-lang/sdk/issues/45371). Consequence for the port: **adding a bound to `TData` removes the only diagnostic a consumer could turn on.**

**The diagnostics.** https://dart.dev/tools/diagnostics lists seven `inference_failure_*` codes, all gated on `strict-inference`:

| Code | Message |
|---|---|
| `inference_failure_on_instance_creation` | The type argument(s) of the constructor '{0}' can't be inferred. |
| `inference_failure_on_function_invocation` | The type argument(s) of the function '{0}' can't be inferred. |
| `inference_failure_on_generic_invocation` | (a generic function-typed expression invoked without type arguments; `generic_inferrer.dart:664-669`) |
| `inference_failure_on_collection_literal` | The type argument(s) of '{0}' can't be inferred. |
| `inference_failure_on_function_return_type` | |
| `inference_failure_on_uninitialized_variable` | The type of '{0}' can't be inferred without either a type or initializer. |
| `inference_failure_on_untyped_parameter` | The type of '{0}' can't be inferred; a type must be explicitly provided. |

The first two are the ones the port's shapes produce (constructor → `_on_instance_creation`; static factory or generic function such as `QueryController.create` or a hooks-style `useState()` → `_on_function_invocation`, rows B2, G3). They are warnings, not errors, so even a consumer who enables the mode gets a yellow line, not a failed build, unless they also promote it (`analyzer: errors: inference_failure_on_instance_creation: error`).

**What the consumer's `analysis_options.yaml` needs, and why the library cannot supply it.** The consumer must write `analyzer: language: strict-inference: true` in *their* file. The dependent-package experiment above shows a library's own setting does not propagate; the analyzer team says the same on the record — "One characteristic of `strict-raw-types` is that it only impacts the package for which it is enabled. An annotation, on the other hand, would impact all clients of the API no matter which package they're in" (bwilkerson, 2022-03-28, on https://github.com/dart-lang/language/issues/2171). That issue, "Prohibit 'automatic-dynamic' behaviour for generic types" (open since 2022-03-28), proposes exactly what this port would want — a per-class `strict T` or annotation that makes an uninferrable argument an error for every client — and has no decision. The only annotation that exists points the other way: `@optionalTypeArgs` from `package:meta` (1.19.0, `lib/meta.dart:430-440`, "Tools such as the analyzer and linter can use this information to suppress warnings that would otherwise require type arguments to be provided"), and the reporting code checks it (`generic_inferrer.dart:616-617`, `!type.element.metadata.hasOptionalTypeArgs`). So a library can *relax* the check for its consumers, never tighten it. Neither `lints/core.yaml` nor `lints/recommended.yaml` (lints 6.1.0, 2026-01-30; https://github.com/dart-lang/core/blob/main/pkgs/lints/lib/recommended.yaml) nor `flutter_lints/flutter.yaml` (6.0.0, which only includes `lints/recommended`) enables any of the three modes; the proposal to add `strict-inference` to the recommended set is dart-lang/core#809, open since 2023-09-19 with "he considered this a clear win" (devoncarew, 2023-10-24) and no action since (https://github.com/dart-lang/core/issues/809). The `strict_top_level_inference` lint that *did* land in `lints/core` 6.0.0 (dart-lang/core#836, dart-lang/sdk#59562) concerns omitted *declared* types on top-level and member declarations, not type arguments — it was active in the consumer run (lints 6.1.0) and said nothing.

## 2. Language-level tricks, one by one

| Trick | Prevents the C1 call site? | Verified by | Ergonomic cost |
|---|---|---|---|
| Bound `TData extends Object?` | **No, and it hides the warning.** Slot becomes `Object?`; `strict-inference` is silent (sdk#52640); `Query<Object?>` is as wrong for a later `getQueryData<int>` as `Query<dynamic>`. | rows E1, F1 | none — which is the problem |
| Bound `TData extends Object` | No; `Object`, warning silent. Also forbids nullable data. | row F1 | breaks `select` returning nullable |
| F-bound `TData extends TQueryData` | Fixes the no-`select` case (`int`) but forbids any `select` that changes the type (`int → String` is a compile error). | rows H1, H2 | unusable: `select` exists to project to other types (upstream's `select: (data) => data.length`) |
| Static factory `.simple<T>` fixing `TData = TQueryData` | Only for callers who use it; the public constructor still infers `<int, dynamic>`. A named constructor cannot do this — Dart constructors carry no type parameters of their own, so it has to be a static method, which cannot be invoked `const`. | rows B1–B3 | loses `const` for inline options; two documented spellings of the same thing; the trap stays |
| Private constructor + statics only | Yes — construction without a source for `TData` is impossible. | rows I1, I2 | same `const` loss; every option object is built through a static; subclassing (`class MyOptions<T> extends QueryObserverOptions<T, T>`, which the deep-dive's consumer probe does) needs a public or `protected` constructor and reopens the hole |
| Separate `SelectQueryOptions<TQueryData, TData>` with **required** `select`; one-slot `QueryOptions<T>` for everything else | Yes for the two-slot type: omitting `select` is `missing_required_argument`, a compile error under any lint set. The one-slot type infers from `queryFn`; the only residue is a key-only observer with neither `queryFn` nor a type argument (row C2), which is the same residue the mutation side and every library in §3 accept, and which `strict-inference` still flags. | rows C1–C4 | the binding already has this split in its widgets (`QueryBuilder<TData>` vs `QuerySelectBuilder<TQueryData, TData>`, `query_builder.dart:37,151`); only the options type does not mirror it. `placeholderData` is `PlaceholderData<TQueryData>`, so it stays on the one-slot type. Breaking now, impossible after 0.1.0 |
| Runtime `assert(TData != dynamic, …)` at the binding boundary | Detects, does not prevent: fails the first debug run or widget test with a message that names the cure; is compiled out of release/AOT builds (`dart compile exe` constructed `ControllerD<int, dynamic>` silently). Misses `Object?` (row E1) — and dart-lang/language#4197 documents that the spec actually says an unconstrained parameter should solve to `Object?`, with lrhn on core#809 calling `strict-inference` "a good stepping stone towards changing the instantiate-to-bounds to choosing `Object?`", so a future Dart could turn every `dynamic` here into `Object?` and walk past this assert. A top-type test survives that: `bool isTopType<T>() => <Object?>[] is List<T>;` returns `true` for `dynamic`, `Object?` and `void`, `false` for `Object`, `int`, `int?` (verified). | row D1, `k_topcheck.dart` | zero at the call site; a backstop, not a guard |
| `@useResult`-style annotation | None exists. `package:meta` 1.19.0 has no annotation that requires type arguments; the analyzer's own annotation (`@optionalTypeArgs`) suppresses the check. The per-class opt-in is language#2171, undecided since 2022. | `meta.dart` constant list; issue | — |
| An analyzer plugin shipped by the library | Would need the consumer to list the plugin in their `analysis_options.yaml` (https://dart.dev/tools/analyzer-plugins) — the same opt-in problem as `strict-inference`, with more machinery. Not tried. | — | — |

## 3. How comparable libraries avoid it

All four put the output type parameter in a *required* parameter; the two that have a `select` make it a separate entry point with a required selector. Signatures from shallow clones on 2026-09-11 (riverpod `79c8050`, bloc `8fcf54d`, flutter_hooks `6f7344f`, signals.dart `81d64e8`); permalinks use those SHAs.

**riverpod.** `Provider<ValueT>` takes its creator positionally and required: `Provider(this._create, {super.name, …})` with `final Create<ValueT> _create;` (`packages/riverpod/lib/src/providers/provider.dart:17-54`, https://github.com/rrousselGit/riverpod/blob/79c8050156cf9a711377c52e869a933e3c75c9a0/packages/riverpod/lib/src/providers/provider.dart#L17) and `typedef Create<CreatedT> = CreatedT Function(Ref ref);` (`core/provider/provider.dart:16`). `FutureProvider` and `StateProvider` are the same shape (`providers/future_provider.dart:96-137`, `providers/legacy/state_provider.dart:39-77`). `select` is an extension method, not an optional field — `extension ProviderListenableSelect<InT> on ProviderListenable<InT> { ProviderListenable<OutT> select<OutT>(OutT Function(InT value) selector) …` (`core/modifiers/select.dart:70`, https://github.com/rrousselGit/riverpod/blob/79c8050156cf9a711377c52e869a933e3c75c9a0/packages/riverpod/lib/src/core/modifiers/select.dart#L70) — so `OutT` always has a source and `ref.watch<StateT>(ProviderListenable<StateT>)` (`core/ref.dart:725`; `flutter_riverpod/lib/src/core/consumer.dart:480`) is fully typed by the listenable. Code generation sidesteps inference entirely: the generator reads the annotated function's declared return type (`riverpod_analyzer_utils/lib/src/nodes/generated_providers/function.dart:73`) and writes the type arguments out. The repo runs `strict-casts`/`strict-inference`/`strict-raw-types: true` on itself (`analysis_options_without_plugins.yaml:3-6`). No tracker issue about `dynamic` inference was found (searched: "dynamic inference", "type argument inferred", "inferred as dynamic", "Provider<dynamic>", "strict-inference", "select dynamic").

**bloc / flutter_bloc.** `BlocSelector<B extends StateStreamable<S>, S, T>` is a *separate widget* from `BlocBuilder`, and both its `selector` and `builder` are required: `const BlocSelector({required this.selector, required this.builder, Key? key, this.bloc})` with `typedef BlocWidgetSelector<S, T> = T Function(S state);` (`packages/flutter_bloc/lib/src/bloc_selector.dart:7-52`, https://github.com/felangel/bloc/blob/8fcf54dfea7ba51ef04c091d1a27e0da498b29f0/packages/flutter_bloc/lib/src/bloc_selector.dart#L28). `BlocBuilder<B extends StateStreamable<S>, S>` requires `builder` and keeps the optional `buildWhen` as a *consumer* of `S`, never its only source (`bloc_builder.dart:73-81`). `BlocProvider<T extends StateStreamableSource<Object?>>` requires `create` (`bloc_provider.dart:34-38`). `S` is *not* inferred from `B`'s bound — felangel/bloc#560 "BlocBuilder doesn't need to explicitly provide the State type again" (open since 2019-10-10, https://github.com/felangel/bloc/issues/560; maintainer: "I think Dart just has no way to know what the generic type S is unless you define it") — which is why the README always spells `BlocBuilder<BlocA, BlocAState>`; #2144 shows a half-inferred `BlocBuilder<dynamic, int>` in the wild. Because `builder` is required, a wrong `S` is a compile error, not a silent `dynamic`. The repo runs all three strict modes plus `strict_top_level_inference` on itself (`analysis_options.yaml:5-8`).

**flutter_hooks.** Every hook's `T` sits in a required positional: `T useValueListenable<T>(ValueListenable<T> valueListenable)` (`listenable.dart:8`, https://github.com/rrousselGit/flutter_hooks/blob/6f7344fc09f3800c1a9944d06ae56d5324e084e3/packages/flutter_hooks/lib/src/listenable.dart#L8); `ValueNotifier<T> useState<T>(T initialData)` — required, not `[T? initialData]`, so `useState()` does not compile and the G3 case cannot arise (`primitives.dart:267`); `T useMemoized<T>(T Function() valueBuilder, [List<Object?> keys = const <Object>[]])` (`primitives.dart:57-60`); `AsyncSnapshot<T> useFuture<T>(Future<T>? future, {T? initialData, bool preserveState = true})` and `useStream` likewise (`async.dart:25-29, 147-151`). The residue is `useState(null)` → `ValueNotifier<Null>`, which the docs handle by writing `useState<int?>(null)`. Strict modes on itself: yes (`packages/flutter_hooks/analysis_options.yaml:6-9`).

**signals.** `Signal<T> signal<T>(T value, {…})` (`packages/signals_core/lib/src/core/signal.dart:392-399`, https://github.com/rodydavis/signals.dart/blob/81d64e880e025863c3ab275337ed482e55f8d980/packages/signals_core/lib/src/core/signal.dart#L392) and `Computed<T> computed<T>(ComputedCallback<T> compute, {…})` (`computed.dart:593-600`) both take the source positionally. The "no value yet" case is split into its own entry point, `Signal<T> lazySignal<T>({…})` (`signal.dart:418-424`) — and that is the one shape in the four libraries that matches ours: called bare it produces `Signal<dynamic>` (verified against `signals_core` 7.0.0), its dartdoc always writes the type argument, and signals is also the only one of the four that does not run `strict-inference` on itself (`packages/signals_core/analysis_options.yaml` is `lints/recommended` plus three rules). `signal(null)` infers `Signal<Null>`; the docs write `signal<String?>(null)`. No `dynamic`-inference issue found (closest: rodydavis/signals.dart#34, about naming inferred types for `always_specify_types`).

## 4. Dart 3.11 – 3.13 (current stable 3.13.3, 2026-09-01)

Read from `CHANGELOG.md` on `dart-lang/sdk` `main` (https://github.com/dart-lang/sdk/blob/main/CHANGELOG.md), sections 3.11.0 through the unreleased 3.14.0:

- **3.11.0:** "There are no language changes in this release."
- **3.12.0:** private named parameters (`Point({required this._x})`).
- **3.13.0:** primary constructors (`class Point(var int x, var int y);`) — a brevity feature, "There are no new semantics"; plus one promotion-soundness fix. Analyzer: "A `no_raw_types` lint rule is introduced, which replaces the `strict-raw-types` analysis option" and "A `no_dynamic_casts` lint rule is introduced, which replaces the `strict-casts` analysis option" (dart-lang/sdk#63516 and #63527, both opened 2026-06). **`strict-inference` has no replacement lint** — no such issue exists (searched dart-lang/sdk: "Replace strict-inference", "strict-inference lint rule replace") — so it stays an `analyzer: language:` mode with the same package-local scope.
- **3.14.0 (unreleased):** library additions only.

Nothing in any of these releases touches inference of type arguments from omitted arguments; grepping the four sections for "infer", "type argument", "dynamic" finds only the `JSExportedDartFunction<T>` generic and dart2wasm notes. The nearest language-level movement is the *opposite* of a guard: dart-lang/language#4197 (2024-12) records that the inference spec's greatest closure would solve an unconstrained parameter to `Object?` where the implementation picks `dynamic`, and the analyzer team frames `strict-inference` adoption as a step toward that change (lrhn on core#809, 2024-02-07). If it lands, `assert(TData != dynamic)` becomes a no-op while the cache still gets a top-typed `Query`.

## Recommendation for this port

Take the structural fix, not a guard: give the four one-slot entry points (`QueryBuilder<TData>`, `context.query`, `watchQuery`, `QueryController.create`) a one-slot options type inferred from `queryFn`, and keep the two-slot type for the select paths (`QuerySelectBuilder`, `selectQuery`, `watchSelectQuery`, `QueryController(...)`) with `select` **required** — the deep-dive's option 1, what #21 already described, what the mutation side already does with `MutationOptions.simple`, and the shape every surveyed library uses (riverpod's `select`, bloc's `BlocSelector`). It is the only variant in the table that makes the C1 call site a compile error under *any* lint set, it is breaking now and impossible after the 0.1.0 tag, and the widget split it mirrors already exists. Do not add a bound to `TData` (it silences the one consumer-side diagnostic, sdk#52640) and do not rely on a static factory alone (row B3). Keep a debug backstop at the binding boundary for the residue that no shape can remove — a key-only observer with neither `queryFn` nor a type argument — written as a top-type test (`<Object?>[] is List<TData>`) rather than `TData != dynamic`, with a message naming the cure, and record in `PORTING_NOTES.md` that it is compiled out of release builds. In the README and `first-query.md`, say once that the type comes from `queryFn`'s return type or an explicit type argument, and recommend `analyzer: language: strict-inference: true` to consumers as the thing that turns the residue into a warning; that is the most a library can do, because a package cannot enable it for its dependents.
