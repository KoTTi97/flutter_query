## 1. `package:fake_async` (1.3.3) and `package:clock` (1.1.2)

**What it intercepts.** `FakeAsync.run` wraps the callback in `runZoned` with a `ZoneSpecification` that overrides exactly three hooks: `createTimer`, `createPeriodicTimer`, and `scheduleMicrotask` (`fake_async.dart` lines 181–191). Every `Timer`, `Timer.periodic`, `Future.delayed`, `Future(...)`, `Future.microtask`, `await`, `Stream` timer, and any other `dart:async` primitive is built on those three zone hooks, so all of them are captured. The doc comment states the intended contract: "All [Future]s, [Stream]s, [Timer]s, microtasks, and other time-based asynchronous features used within [callback] are controlled by calls to [elapse] rather than the passing of real time" (lines 26–28).

**What it does *not* intercept.** `DateTime.now()` and `Stopwatch` are not zone hooks and are not touched. fake_async's only clock integration is through `package:clock`: the constructor builds `_clock = Clock(() => nonNullInitialTime.add(elapsed))` (lines 105–107) and `run` calls `withClock(_clock, ...)` (line 182). `package:clock`'s top-level `clock` getter is `Zone.current[_clockKey] as Clock? ?? const Clock()` (`clock/lib/src/default.dart` line 31), and `withClock` installs the fake via `runZoned(callback, zoneValues: {...})` (lines 45–52). So `clock.now()` (and `clock.stopwatch()`, which is built on the same `Clock`) read fake time; `DateTime.now()` reads wall-clock time.

**A stray `DateTime.now()`** therefore returns the real wall-clock instant, which is frozen relative to fake time. Any `staleTime`/`gcTime`/`dataUpdatedAt` arithmetic that mixes a `DateTime.now()` sample with `clock.now()` samples silently diverges by however much fake time has been elapsed, with no error. (Consequence of lines 105–107 and `default.dart` line 31: there is no interception, only a zone value.)

**`elapse` vs `flushMicrotasks` vs `flushTimers`.**

- `elapse(duration)`: "Any timers created within [run] or [fakeAsync] will fire if their time is within [duration]. The microtask queue is processed before and after each timer fires." (lines 129–131). Implementation: `_fireTimersWhile((next) => next._nextCall <= _elapsingTo!)` then `_elapseTo(_elapsingTo!)` (lines 140–142). Timers are fired in `_nextCall` order (`minBy`, line 243), and fake time is moved to each timer's due time *before* it fires (line 246), so `clock.now()` inside a callback reports the timer's scheduled time, not the target of the `elapse`.
- `flushMicrotasks()`: drains `_microtasks` until empty; "Does not run timers." (lines 197–202).
- `flushTimers({timeout = 1h, flushPeriodicTimers = true})`: "Elapses time until there are no more active timers", throwing `StateError('Exceeded timeout ...')` if fake time would pass `timeout` (lines 204–232).
- `elapseBlocking(duration)`: moves the clock without running anything ("Neither timers nor microtasks are run during this call", lines 146–161).

**`elapse` is not re-entrant.** `elapse` sets `_elapsingTo` for the duration of the call and starts with:

```dart
} else if (_elapsingTo != null) {
  throw StateError('Cannot elapse until previous elapse is complete.');
}
```

(`fake_async.dart` lines 136–138; doc at lines 127–128: "Throws a [StateError] if a previous call to [elapse] has not yet completed.") A timer or microtask callback that calls `elapse` while an outer `elapse` is on the stack therefore throws. `flushMicrotasks` and `elapseBlocking` have no such guard.

**Zero-duration and negative timers.** `FakeTimer._` clamps negative durations to zero and sets `_nextCall = _async._elapsed + duration` (lines 332–341), so a `Timer(Duration.zero)` is due immediately but only fires from `_fireTimersWhile`, i.e. inside `elapse`/`flushTimers`, never from `flushMicrotasks`. Periodic fake timers are isochronous: `_nextCall += duration` and missed periods are skipped with `_tick` incremented (lines 351–360; the class doc says "This behavior matches VM timers", lines 278–283).

**What this means for the port.** Every time read must go through `clock.now()` and every delay through `Timer`/`Future.delayed` (design decision D10 is correct and sufficient); and a driver that needs to advance time from inside a callback must hand control back to an outer loop instead of calling `elapse` re-entrantly, which is exactly what `testFakeAsync`'s `await time.advance(d)` exists for.

## 2. `Timer(Duration.zero)` versus JavaScript `setTimeout(0)`

**What Dart specifies.** The `Timer` class doc: "A negative duration is treated the same as [Duration.zero]. If the duration is statically known to be 0, consider using [run]" (`sdk/lib/async/timer.dart` lines 13–14) and `Timer.run`: "Runs the given [callback] asynchronously as soon as possible. This function is equivalent to `new Timer(Duration.zero, callback)`" (lines 98–100, 107). For the JS target: "If Dart code using Timer is compiled to JavaScript, the finest granularity available in the browser is 4 milliseconds" (lines 25–26). `Future.delayed` adds: "If the duration is 0 or less, it completes no sooner than in the next event-loop iteration, after all microtasks have run" (`sdk/lib/async/future.dart` lines 404–406). Dart therefore guarantees ordering (after all microtasks, in a later event-loop turn) but promises no minimum delay.

**What the VM does** (`sdk/lib/_internal/vm/lib/timer_impl.dart`). Zero-millisecond timers live in a separate linked list, not the heap: "Timers with a timeout value of > 0 do end up on the TimerHeap. Timers with a timeout of 0 are queued in a list" (lines 141–142). Their wakeup time is `now` (no +1 rounding, line 206), and enqueueing sends one port message per timer: "Every zero timer gets its own event" / `_sendPort!.send(_ZERO_EVENT)` (lines 277–278, 289–294). Each `_ZERO_EVENT` is a normal isolate message, so other messages already in the isolate's port queue interleave with a chain of zero timers; a zero timer created from inside a timer callback is "enqueued now and notified in the next spin at the earliest" (lines 387–388). When a zero event is handled, any heap timers that expired earlier are run first ("Make sure to also execute non-zero timers with a lower expiration time", lines 296–297), and the microtask queue is drained after every timer callback (`_runPendingImmediateCallback()`, line 429). Non-zero timers are given `wakeupTime = now + 1 + milliSeconds` (line 206) so they never fire early at millisecond resolution.

**What dart2js/DDC do.** `_TimerImpl` calls `self.setTimeout(callback, milliseconds)` directly for all durations including zero (`sdk/lib/_internal/js_runtime/lib/async_patch.dart`, `_TimerImpl` constructor), so on the web Dart's zero timer *is* `setTimeout(0)` and inherits the browser clamp. Microtasks use a separate `_AsyncRun` path (MutationObserver, then `setImmediate`, then a zero timer as last resort).

**What JavaScript specifies.** HTML Standard, "timer initialization steps": step 4 "If timeout is less than 0, then set timeout to 0"; step 5 "If nestingLevel is greater than 5, and timeout is less than 4, then set timeout to 4" (https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timer-initialisation-steps). MDN restates it as a 4 ms minimum "once a nested call to setTimeout has been scheduled 5 times" and documents background-tab throttling (Firefox desktop 1 s minimum, Chrome tiered) (https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout#reasons_for_delays_longer_than_specified). Node: "When delay is larger than 2147483647 or less than 1 or NaN, the delay will be set to 1" (https://nodejs.org/api/timers.html#settimeoutcallback-delay-args), and `setImmediate` callbacks queued from inside an executing callback "will not be triggered until the next event loop iteration".

**Starvation.** A zero timer cannot starve the Dart event loop the way a recursive microtask can, because each zero timer is its own event (lines 277–278, 387–388). A recursive `scheduleMicrotask`, by contrast, does starve timers: the `scheduleMicrotask` doc's example "Timer.run(() { print("executed"); }); // Will never be executed." (`sdk/lib/async/schedule_microtask.dart` lines 127–135).

**What this means for the port.** Upstream's `setTimeout(0)` idioms (e.g. the notify batching and `sleep(0)` in tests) map to `Timer(Duration.zero)`/`Future.delayed(Duration.zero)` with the same "after all microtasks, next event-loop turn" ordering and no 1–4 ms floor on the VM; ported tests that upstream wrote with `vi.advanceTimersByTime(0)` or `await sleep(0)` need an `elapse(Duration.zero)` (which runs due zero timers) rather than a `flushMicrotasks()`.

## 3. Microtask versus event-queue ordering; `await`; Dart `Future` versus JS `Promise`

**Two queues, microtasks first.** `scheduleMicrotask`: "Callbacks registered through this function are always executed in order and are guaranteed to run before other asynchronous events (like [Timer] events, or DOM events)" (`sdk/lib/async/schedule_microtask.dart` lines 123–125), with the starvation warning quoted in section 2. The VM drains the microtask queue after each timer callback (`timer_impl.dart` line 429). dart.dev describes the outer loop: "all events are added to a queue, called the event queue ... the event loop processes events in the order they're queued, one at a time" (https://dart.dev/language/concurrency#event-loop).

**Futures never complete synchronously into listeners.** `Future.then`: "If this future is already completed, the callback will not be called immediately, but will be scheduled in a later microtask" (`sdk/lib/async/future.dart` lines 757–758). Implementation: `_Future._addListener` on a completed future does `// Handle late listeners asynchronously.` `_zone.scheduleMicrotask(() { _propagateToListeners(this, listener); })` (`sdk/lib/async/future_impl.dart` lines 541–544). `Future.value(v)` creates a future that is *already* completed ("equivalently to `new Future<T>.sync(() => value)`", `future.dart` lines 352–354; `_Future<T>.immediate(...)`, line 372) but listeners attached to it still run in a later microtask. `Future.sync` runs the computation synchronously and returns a completed future (lines 322–336); `Future.microtask` uses `scheduleMicrotask` (lines 271–282); `Future()` uses `Timer.run` (lines 244–255); `Future.error` completes "in a future microtask" (lines 375–378).

**How `await` schedules (VM).** `_SuspendState._await` in `sdk/lib/_internal/vm/lib/async_patch.dart`: awaiting a non-`Future` value schedules the continuation with `zone.scheduleMicrotask(run)` (`_awaitNotFuture`, lines 278–289); awaiting an already-completed `_Future` also goes through `future._zone.scheduleMicrotask(run)` (`_awaitCompletedFuture`, lines 238–276); awaiting an uncompleted `_Future` attaches directly via `_thenAwait` (lines 320–323); awaiting a user-defined `Future` subclass uses `.then` (`_awaitUserDefinedFuture`, line 293). So `await x` always yields at least one microtask, exactly like `await` in JS, and `async` functions run synchronously until the first `await` ("the async function executes only until it encounters its first await expression. Then it returns a Future object", https://dart.dev/language/async).

**Differences from JS `Promise` worth knowing.** (a) Dart has no analogue of a Promise's *synchronous* `Promise.resolve(x)` identity semantics: `Future.value(future)` chains rather than returning the argument (`future.dart` lines 345–349). (b) Dart's `Completer.sync` can complete a future synchronously and run listeners synchronously (`future.dart` lines 1219–1240) — JS has no such API; the port must not use it for anything that upstream expects to be async. (c) Dart's `Future.sync` executes its callback synchronously *and* returns a completed future, which JS `Promise.resolve().then(fn)` does not do. (d) Zone-scoped error routing (section 4) has no Promise counterpart.

**What this means for the port.** JS `await`/`.then` microtask interleavings in `query-core` (e.g. `notifyManager.batch`, the retryer's `Promise.resolve().then(...)` hops) have one-to-one Dart equivalents, so ported tests' `await Promise.resolve()`/`flushPromises` steps become `await Future.value()`/`flushMicrotasks()`; the port must avoid `Completer.sync` and `Future.sync` where upstream depends on a Promise tick.

## 4. Unhandled async errors: `Zone.handleUncaughtError`, `Future.ignore()`, `package:test`

**How a listener-less failed future becomes uncaught.** `Future` class doc: "If a future does not have any registered handler when it completes with an error, it forwards the error to an 'uncaught-error handler'. This behavior ensures that no error is silently dropped. However, it also means that error handlers should be installed early" (`sdk/lib/async/future.dart` lines 167–170; also lines 111–115: "an asynchronous error that no-one is awaiting is an *uncaught* error and may terminate the running program"). Implementation: `_Future._propagateToListeners` with `listeners == null`:

```dart
if (hasError && !source._ignoreError) {
  AsyncError asyncError = source._error;
  source._zone.handleUncaughtError(asyncError.error, asyncError.stackTrace);
}
```

(`sdk/lib/async/future_impl.dart` lines 845–850). Propagation itself is what was scheduled in a microtask, so the uncaught report happens one microtask after the error completion; a `.catchError`/`then(onError:)` attached synchronously in the same turn still counts as "early". `Zone.handleUncaughtError` doc: "By default, when handled by the root zone, uncaught asynchronous errors are treated like uncaught synchronous exceptions" (https://api.dart.dev/dart-async/Zone/handleUncaughtError.html). The dart.dev guide's rule of thumb: "It is crucial that error handlers are installed before a Future completes" (https://dart.dev/libraries/async/futures-error-handling#potential-problem-failing-to-register-error-handlers-early).

**`Future.ignore()`** (since Dart 2.14): "Completely ignores this future and its result. ... Simply ignoring a future can result in uncaught asynchronous errors. This method instead handles (and ignores) any values or errors coming from this future ... If you merely want to silence the 'unawaited futures' lint, use the [unawaited] function instead. That will ensure that an unexpected error is still reported" (`future.dart` lines 1108–1122). For an SDK `_Future` it sets `_stateIgnoreError` on the future and its chain source (`future_impl.dart` `_ignore()` line 426; checked at line 846); for other implementations it attaches no-op `then`/`onError` handlers (lines 1124–1130). `unawaited()` does **not** suppress the error.

**How `package:test` (1.31.2) treats them.** README, "Uncaught Async Errors": "Any uncaught asynchronous error throws within the zone that a test is running in will cause the test to be considered a failure. This can cause a test which was previously considered complete and passing to change into a failure if the uncaught async error is raised late. If all test cases within the suite have completed this may cause some errors to be missed, or to surface in only some runs" (`test-1.31.2/README.md` lines 430–437). Mechanism: `Invoker.guard` installs a `handleUncaughtError` zone hook that looks up `zone[#test.invoker]` and routes the error to that test's `_handleError`; if no invoker is in scope it re-raises to the parent zone (`test_api-0.7.13/lib/src/backend/invoker.dart` lines 201–217). A late error on a finished test is reported as "This test failed after it had already completed. Make sure to use a matching library which informs the test runner of pending async work." (lines 428–433). Errors that escape every test zone reach the runner's suite channel, whose handler calls `loadSuiteZone.handleUncaughtError(...)`, which "will cause the virtual load test to fail, which will notify the user of the error" (`test_core-0.6.19/lib/src/runner/plugin/platform_helpers.dart` lines 74–84) — i.e. the *file's* load test fails, not an individual test. Each test file runs in its own isolate (`test_core-0.6.19/lib/src/runner/vm/platform.dart`, `_spawnIsolate`).

**What this means for the port.** Every future the core creates and does not hand to a caller (retryer promises, `refetch()` results dropped by `invalidateQueries`, mutation `execute()` calls) must get `.ignore()` — not merely `unawaited()` — at the point where nobody will await it, otherwise a rejected future fails whichever test is running at the time, or the file's load test if none is (D13 is well-founded; the granularity is test-or-file, not always file).

## 5. `SchedulerBinding.schedulerPhase`, `addPostFrameCallback`, `scheduleFrame`, and when `markNeedsBuild` throws

Sources: `packages/flutter/lib/src/scheduler/binding.dart` and `packages/flutter/lib/src/widgets/{framework,binding}.dart` at Flutter 3.38.8.

**Phases.** `SchedulerPhase` values and doc (https://api.flutter.dev/flutter/scheduler/SchedulerPhase.html): `idle` — "No frame is being processed. Tasks ..., microtasks ..., Timer callbacks, event handlers ..., and other callbacks (e.g. from Futures, Streams, and the like) may be executing"; `transientCallbacks` — animation tickers; `midFrameMicrotasks` — "Microtasks scheduled during the processing of transient callbacks are current executing"; `persistentCallbacks` — "Typically, this is the build/layout/paint pipeline"; `postFrameCallbacks` — "Typically, these callbacks handle cleanup and scheduling of work for the next frame". The transitions are literal assignments: `handleBeginFrame` asserts `idle`, sets `transientCallbacks`, then `midFrameMicrotasks` in a `finally` (binding.dart lines 1255–1276); `handleDrawFrame` asserts `midFrameMicrotasks`, sets `persistentCallbacks`, then `postFrameCallbacks`, copies-and-clears `_postFrameCallbacks` before invoking them, and sets `idle` in a `finally` (lines 1340–1369). `WidgetsBinding.drawFrame`'s doc lists the ten sub-phases (build, layout, compositing bits, paint, compositing, semantics, finalize tree, then post-frame callbacks) (widgets/binding.dart lines 1165–1226).

**`addPostFrameCallback`.** "This method does *not* request a new frame. If a frame is already in progress and the execution of post-frame callbacks has not yet begun, then the registered callback is executed at the end of the current frame. Otherwise, the registered callback is executed after the next frame (whenever that may be, if ever)." Callbacks run "in the order in which they have been added", are called "exactly once", and cannot be unregistered (scheduler/binding.dart lines 789–805, 820–836).

**`scheduleFrame` / `ensureVisualUpdate`.** `scheduleFrame()` returns early if `_hasScheduledFrame || !framesEnabled`, else calls `platformDispatcher.scheduleFrame()` (lines 948–958); "Calling this during a frame forces another frame to be scheduled, even if the current frame has not yet completed" and frames are "serviced when triggered by a 'Vsync' signal" and may be delayed "if the device's screen is turned off" (lines 927–941). `ensureVisualUpdate()` schedules a frame only in `idle` or `postFrameCallbacks` and is a no-op in the three mid-frame phases (lines 901–920). `framesEnabled` is driven by lifecycle: `handleAppLifecycleStateChanged` enables frames for `resumed`/`inactive` and disables them for `hidden`/`paused`/`detached` (lines 414–428).

**When "setState() or markNeedsBuild() called during build" is thrown.** `Element.markNeedsBuild` (widgets/framework.dart lines 5342–5391), in an `assert` (debug/profile only):

- If `owner._debugBuilding` is true (set only inside `BuildOwner.buildScope`, lines 3062–3073, and cleared in its `finally`), the call is allowed when the target `_debugIsDescendantOf(owner._debugCurrentBuildTarget)` — i.e. the element currently being rebuilt (set at line 5528 in `Element.rebuild`) or one of its descendants — and otherwise throws `'setState() or markNeedsBuild() called during build.'` (lines 5350–5375). The message explains why: "A widget can be marked as needing to be built during the build phase only if one of its ancestors is currently building."
- Else if `owner._debugStateLocked` (`_debugStateLockLevel > 0`, incremented by `lockState` and by `buildScope`, lines 2999, 3013–3027, 3071) it throws `'setState() or markNeedsBuild() called when widget tree was locked.'` (lines 5376–5385). `lockState` is used e.g. around `State.dispose` (doc, lines 3010–3012) and unmounting inactive elements (line 3344).

**`didChangeDependencies` / `didUpdateWidget`.** Both are invoked from `StatefulElement` during the element's own rebuild (`state.didChangeDependencies()` at lines 5971, 5982; `state.didUpdateWidget(oldWidget)` at line 5994), while `_debugCurrentBuildTarget` is that element, so `setState` on the *same* `State` there passes the descendant check and does not throw (the `State` doc merely calls it redundant: "The framework always calls [build] after calling [didUpdateWidget], which means any calls to [setState] in [didUpdateWidget] are redundant", lines 1024–1025). Calling `setState`/`markNeedsBuild` on an *ancestor* or unrelated element from those hooks throws the "during build" error.

**Layout / paint.** `_debugBuilding` and the state lock are released when `buildScope` returns, before `super.drawFrame()` runs layout and paint (widgets/binding.dart lines 1262–1265), so `markNeedsBuild` itself does not throw there. Instead `BuildOwner.scheduleBuildFor` calls `onBuildScheduled` when `_scheduledFlushDirtyElements` is false (framework.dart lines 2985–2988; the flag is reset in `buildScope`'s `finally`, line 3114), and `WidgetsBinding._handleBuildScheduled` asserts `!debugBuildingDirtyElements`, throwing `'Build scheduled during frame.'` — "This might be because setState() was called from a layout or paint callback" — because `debugBuildingDirtyElements` is true from the start of `drawFrame` through `finalizeTree` (widgets/binding.dart lines 1121–1150, 1227–1272). The same message recommends `SchedulerBinding.addPostFrameCallback` for "the one frame delay". During `postFrameCallbacks` the flag is already false (it is cleared in `drawFrame`'s `finally`, which runs inside the persistent-callback phase), so `setState` from a post-frame callback is legal and `ensureVisualUpdate` schedules the next frame.

**What this means for the port.** A cache notification that arrives while `schedulerPhase == persistentCallbacks` (or `transientCallbacks`/`midFrameMicrotasks`) must not call `setState`/`markNeedsBuild` on the subscribing element unless that element is the one being built; deferring it with `addPostFrameCallback` and delivering in `idle`/`postFrameCallbacks` is safe in every phase, and since `addPostFrameCallback` never requests a frame, the binding must call `scheduleFrame`/`ensureVisualUpdate` (or rely on the `setState` it performs) to make the deferred update visible.

## 6. `AppLifecycleListener` and `AppLifecycleState` (`detached`, `resumed`, `inactive`, `hidden`, `paused`)

**The enum and its state machine.** `dart:ui` `AppLifecycleState` (Flutter 3.38.8, `bin/cache/pkg/sky_engine/lib/ui/platform_dispatcher.dart` lines 2198–2333): "States not supported on a platform will be synthesized by the framework when transitioning between states which are supported, so that all implementations share the same state machine." The initial value is `detached`, "updated to the current state (usually [resumed]) as soon as the first lifecycle update is received from the platform." Per value:

- `detached`: "only entered on iOS, Android, and web, although on all platforms it is the default state before the application begins running."
- `resumed`: on Android "the Flutter host view having focus (Activity.onWindowFocusChanged was called with true) while in Android's 'resumed' state"; "On iOS and macOS, this corresponds to the app running in the foreground active state."
- `inactive`: "At least one view of the application is visible, but none have input focus." iOS/macOS: "when in a phone call, when responding to a TouchID request, when entering the app switcher or the control center". Android: `Activity.onPause` has been called, or resumed but without window focus — "partially obscured", "split screen", "phone call", "picture-in-picture", "system dialog", "notification window shade is down, or the application switcher is visible". "On Android and iOS, apps in this state should assume that they may be [hidden] and [paused] at any time."
- `hidden`: "All views of an application are hidden, either because the application is about to be paused (on iOS and Android), or because it has been minimized or placed on a desktop that is no longer visible (on non-web desktop), or is running in a window or tab that is no longer visible (on the web). On iOS and Android ... a transition to this state is synthesized before the [paused] state is entered when coming from [inactive], and before the [inactive] state is entered when coming from [paused]."
- `paused`: "the engine will not call the onBeginFrame and onDrawFrame callbacks. This state is only entered on iOS and Android."

The framework enforces the allowed edges in `ServicesBinding._debugVerifyLifecycleChange`: `resumed → inactive`; `inactive → resumed | hidden`; `hidden → paused | inactive`; `paused → hidden | detached`; `detached → resumed | paused` (`packages/flutter/lib/src/services/binding.dart` lines 359–380). `_generateStateTransitions` walks the enum order to insert intermediate states when the embedder skips one (lines 312–361) — this is where `hidden` is synthesized on iOS/Android — and each generated state is dispatched in turn (lines 302–310). "Applications should not rely on always receiving all possible notifications" (enum doc, lines 2223–2228).

**`AppLifecycleListener`** (`packages/flutter/lib/src/widgets/app_lifecycle_listener.dart`) exposes `onStateChange` plus edge callbacks: `onResume` (any → `resumed`), `onInactive` (`resumed` → `inactive`), `onShow` (`hidden` → `inactive`), `onHide` (`inactive` → `hidden`), `onRestart` (`paused` → `hidden`), `onPause` (`hidden` → `paused`), `onDetach` (→ `detached`), and `onExitRequested` (lines 213–270; the class asserts the same transition table). Callback docs: `onHide` "On mobile platforms, this is usually just before the application is replaced by another application in the foreground. On desktop platforms, this is just before the application is hidden by being minimized ... On the web, this is just before a window (or tab) is hidden" (lines 114–122). Added in Flutter 3.13 (release notes: "Add `AppLifecycleListener`, with support for application exit handling" flutter/flutter#123274 and "Prepare for adding values to AppLifecycleState" flutter/flutter#119954, https://docs.flutter.dev/release/release-notes/release-notes-3.13.0); the `hidden` value landed in the same cycle (flutter/flutter#127987 "Fix handling of AppLifecycleState.hidden", merged 2023-05-31, before 3.13.0's August 2023 release).

App switcher or Control Center alone stops at `inactive`. |
| Android | `FlutterActivityAndFragmentDelegate.java`: `onResume` → `appIsResumed`, `onPause` → `appIsInactive`, `onStop` → `appIsPaused`, `onDetach` → `appIsDetached`, `onWindowFocusChanged` → `aWindowIsFocused`/`noWindowsAreFocused`; `LifecycleChannel.java` combines them (`resumed` + focus → `resumed`, `resumed` without focus → `inactive`; other states ignore focus) | Home/app switcher/lock: `resumed → inactive (focus lost or onPause) → hidden (synth) → paused (onStop)`; notification shade or dialog alone: `inactive`. |
| macOS | `FlutterEngine.mm`: `applicationWillBecomeActive` → `resumed` if visible else `hidden`; `applicationWillResignActive` → `inactive` (or `hidden` if not visible); `NSApplicationDidChangeOcclusionStateNotification` → `resumed`/`inactive` when visible, `hidden` when fully occluded | Cmd-Tab: `resumed → inactive`; minimize/hide/fully covered: `→ hidden`. No `paused`. |
| Windows | `windows_lifecycle_manager.cc`: `WM_SHOWWINDOW`, `WM_SIZE` (`SIZE_MINIMIZED` vs restored/maximized), `WM_SETFOCUS`/`WM_KILLFOCUS`, `WM_DESTROY` update visible/focused sets; state = `kHidden` if no visible windows, `kInactive` if none focused, else `kResumed` | Alt-Tab: `inactive`; minimize: `hidden`. No `paused`/`detached`. |
| Linux | `fl_window_state_monitor.cc`: GDK `WITHDRAWN`/`ICONIFIED` → `hidden`; visible + `GDK_WINDOW_STATE_FOCUSED` → `resumed`, visible unfocused → `inactive` | Same shape as Windows. |
| Web | `lib/web_ui/.../platform_dispatcher/app_lifecycle_state.dart`: window `focus` → `resumed`, `blur` → `inactive`, `visibilitychange` visible → `resumed` / hidden → `hidden`; all views removed → `detached` | Tab switch: `resumed → inactive → hidden` (the framework synthesizes `inactive` if `blur` did not fire first). No `paused`. |

**Does `hidden` exist everywhere?** Yes as an enum value on every platform since Flutter 3.13; it is *emitted natively* by the desktop and web embedders and *synthesized* on iOS/Android around every `paused` transition (enum doc, lines 2311–2322; `_generateStateTransitions`). `paused` and `detached` are never emitted on desktop.

**What this means for the port.** `focusManager`'s "focused" should be `state == AppLifecycleState.resumed` (upstream's `visibilityState === 'visible'` is closest to `!hidden && !paused`, but `inactive` on mobile precedes every backgrounding and covers the app switcher, so treating only `resumed` as focused avoids refetch storms while the switcher is open); use `AppLifecycleListener.onStateChange` (or `WidgetsBindingObserver.didChangeAppLifecycleState`) and rely on the synthesized `hidden` so a single handler works on all six platforms.

## 7. Background execution limits and what happens to Dart `Timer`s

**iOS.** `applicationDidEnterBackground(_:)`: "Your implementation of this method has approximately five seconds to perform any tasks and return. If the method doesn't return before time runs out, your app is terminated and purged from memory" and "Use this method to release shared resources, invalidate timers, and store enough app state information to restore your app" (https://developer.apple.com/documentation/uikit/uiapplicationdelegate/applicationdidenterbackground(_:)). "Extending your app's background execution time": "That method has five seconds to perform any tasks and return. Shortly after that method returns, the system puts your app into the suspended state" and "If you don't end your tasks in a timely manner, the system terminates your app" (https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time). `beginBackgroundTask(withName:expirationHandler:)`: "Apps running background tasks have a finite amount of time in which to run them. (You can find out the maximum background time available using the backgroundTimeRemaining property.) ... If you don't call endBackgroundTask(_:) for each task before time expires, the system kills the app" (https://developer.apple.com/documentation/uikit/uiapplication/beginbackgroundtask(withname:expirationhandler:)). "Preparing your UI to run in the background" tells apps on deactivation to "Suspend dispatch and operation queues. Don't schedule any new tasks for execution. Invalidate any active timers" (https://developer.apple.com/documentation/uikit/preparing-your-ui-to-run-in-the-background). A suspended process runs no threads, so the Dart isolate — and its timer thread — does not run at all.

**Android.** Doze: the system "Suspends network access", "Ignores wake locks", "Defers standard AlarmManager alarms", "Doesn't let JobScheduler run"; it periodically opens a maintenance window and "When the user wakes the device by moving it, turning on the screen, or connecting a charger, the system exits Doze and all apps resume normal activity" (https://developer.android.com/training/monitoring-device-state/doze-standby). Process lifecycle: a cached process (an app whose activities are all stopped) may be killed "as needed when resources like memory are needed elsewhere", and "Starting in Android 13, an app process may receive limited or no execution time until it enters one of the above active lifecycle states" (https://developer.android.com/guide/components/activities/process-lifecycle). Android 8+: "When an app goes into the background, it has a window of several minutes in which it is still allowed to create and use services. At the end of that window, the app is considered to be idle" (https://developer.android.com/about/versions/oreo/background). Background-work guide: "asynchronous work is not guaranteed to finish if the app stops being in a valid lifecycle stage (for example, if the app leaves the foreground)" (https://developer.android.com/develop/background-work/background-tasks). Separately, connectivity_plus notes that on Android 8.0+ connectivity changes are not delivered in the background (see section 8).

**What the Dart VM does when the isolate is not scheduled.** Timers are not dropped: they remain in the heap/zero list with absolute `_wakeupTime`s, and the event-handler thread wakes the isolate with a `_TIMEOUT_EVENT` (`timer_impl.dart` lines 458–465). On handling, `_queueFromTimeoutEvent` collects **every** timer whose `_wakeupTime <= currentTime` (lines 361–368) and `_runTimers` runs them back-to-back in wakeup order, draining microtasks after each (lines 391–430). Overdue one-shot timers therefore fire late and all at once; overdue periodic timers do not replay missed periods — "if (millisecondsOverdue > ms) { int missedTicks = millisecondsOverdue ~/ ms; timer._wakeupTime += missedTicks * ms; timer._tick += missedTicks; }" (lines 414–419) — they fire once and `tick` jumps. In non-product builds a timer that is ≥100 ms overdue posts a diagnostic event (lines 400–404). Timers are only lost if the process is terminated, and Apple/Android both document that a backgrounded process may be terminated without a callback (above; and `AppLifecycleState` doc: "no notification will be sent before the application is suddenly terminated, and some states may be skipped").

**What this means for the port.** A `refetchInterval` or `gcTime` timer that comes due while the app is paused fires in a burst on resume, after which the lifecycle `resumed` transition also triggers `refetchOnWindowFocus`; the binding should (a) treat `hidden`/`paused` as "not focused" so interval refetches are gated by `refetchIntervalInBackground` exactly as upstream, and (b) accept that `dataUpdatedAt`-based staleness uses `clock.now()` at fire time so a burst of late timers computes correct staleness rather than replaying missed periods.

## 8. `connectivity_plus` as an `onlineManager` source; `internet_connection_checker`

**`connectivity_plus` (7.3.1 on pub.dev, 2026-07).** Reports `List<ConnectivityResult>` of interface types — `wifi`, `bluetooth`, `ethernet`, `mobile`, `vpn`, `satellite`, `other`, `none` — via `checkConnectivity()` and `onConnectivityChanged` (https://pub.dev/packages/connectivity_plus). README caveats (https://github.com/fluttercommunity/plus_plugins/blob/main/packages/connectivity_plus/connectivity_plus/README.md):

- "You should not rely on the current connectivity status to decide whether you can reliably make a network request. Connection type availability does not guarantee that there is an Internet access. For example, the plugin might return Wi-Fi connection type, but it might be a connection with no Internet access due to network requirements (like on hotel Wi-Fi networks where user often needs to go through a captive portal to authorize first)."
- VPN: Android reports `vpn`; on iOS/macOS "There is no separate network interface type for [vpn]. It returns [other] on any device (also simulator)"; Windows/Linux report `vpn`. A VPN interface being up says nothing about tunnel reachability.
- iOS/macOS: the observer "can give multiple or unreliable results. For example, reporting connectivity 'none' followed by connectivity 'wifi' right after reconnecting", and the stream may emit duplicates.
- Android: "Connectivity changes are no longer communicated to Android apps in the background starting with Android O. You should always check for connectivity status when your app is resumed."
- Web: uses the experimental NetworkInformation API (not enabled in Firefox; desktop browsers only return effective-type buckets) and falls back to `navigator.onLine`, "which only supports boolean online/offline status", returning either `wifi` or `none`.

**Suitability.** It is a *link-layer* signal with the same semantics as the browser's `navigator.onLine` that upstream `onlineManager` already uses (upstream listens to `online`/`offline` events and treats `false` as authoritative and `true` as "maybe"), so it is a faithful source for `onlineManager.setOnline(results.any((r) => r != ConnectivityResult.none))` provided the port keeps upstream's semantics: offline pauses fetches, online merely allows them, and a real request failure is still handled by the retryer. The false-positive cases above (captive portal, VPN with no route, "connected but no internet") are exactly the ones upstream's `networkMode: 'online'` already tolerates by retrying.

**`internet_connection_checker` (3.0.1 on pub.dev, published ~2024-12).** Instead of interface state it probes reachability: default addresses include `1.1.1.1`, `8.8.4.4`, `208.67.222.222` (and HTTPS URLs on web), default timeout 5 s, default poll interval 5 s, and a `requireAllAddressesToRespond` switch (default: any one success means connected) (https://pub.dev/documentation/internet_connection_checker/latest/internet_connection_checker/InternetConnectionChecker-class.html; https://pub.dev/packages/internet_connection_checker). That makes it a *polling* source that generates network traffic, wakes the isolate every 5 s, and reports "offline" in any environment that blocks those public resolvers (corporate networks, air-gapped labs) — a false negative that would wrongly pause every query. Its `onStatusChange` stream must be disposed manually (README).

**What this means for the port.** Use `connectivity_plus` (edge-triggered, no traffic, mirrors `navigator.onLine`) as the default `onlineManager` event source with `none`-only-means-offline semantics and a re-check on `resumed`; leave reachability probes such as `internet_connection_checker` as an opt-in `onlineManager.setEventListener` replacement, never the default, so that "connected but no internet" surfaces as a retried/failed query rather than a globally paused cache.
